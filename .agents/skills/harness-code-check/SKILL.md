# Harness 代码检查

把工具输出变成可核实的代码问题。默认只读源码，允许检查命令生成临时报告；修复、删除代码或新增检查基础设施需要用户另行要求。

## 1. 固定范围与检查入口

- 读取仓库说明、适用的 `AGENTS.md`、构建与 CI 配置。记录工作目录、HEAD、工作区状态、用户指定的范围。
- 用户指定基线时，解析为 commit，按 merge-base 检查已提交差异，并明确是否包含工作区；未指定时，优先检查暂存、未暂存和未跟踪代码，工作区干净则检查当前仓库。显式全仓请求按全仓执行。
- 变更检查也要追踪相关调用方、导出、注册入口与测试；僵尸判断需要全仓调用图或入口证据，不能只查 diff。
- 从项目脚本、CI 和已安装工具找到 lint、类型检查、密钥扫描、覆盖率和未使用代码分析入口。复用现有命令；缺少工具时用源码搜索缩小候选，再核实语义。先读命令，避开会自动改写源码、部署或写入共享服务的命令。
- 排除依赖目录、缓存和构建产物；生成源码与测试夹具按用途核实，记录会影响结论的排除范围。历史密钥扫描仅在用户要求时执行。

完成条件：范围、入口、适用检查与可运行命令明确。每个适用项都进入下面的检查账本，工具缺失也保留该项。

## 2. 逐项检查

| 检查 | 检测与确认依据 | 常见误报边界 |
| --- | --- | --- |
| 恒等分支 | 用 lint / AST 规则找恒真恒假条件、重复条件和两侧等价的分支。核实可达性、输入约束、短路求值及副作用，说明哪个判断失效、哪个路径被遮蔽或哪个条件多余。 | 文本相同不代表行为相同；getter、函数调用、NaN 等语言语义会影响结论。编译平台条件或明确的防御判断需看上下文。 |
| 静默丢弃错误信息 | 查空 `catch`、无处理的拒绝、忽略错误返回值，以及失败后返回默认值或成功状态的路径。追踪错误如何交给调用方，确认原始原因在哪一层丢失、会造成什么后果。 | 可恢复的探测、取消和 best-effort 清理可能有明确契约；重新抛出或传递给调用方即可，不要求每层重复日志。 |
| 硬编码私钥 / 密钥 | 优先运行已有密钥扫描，扫描范围内源码与配置，包括适用的未跟踪文件。核实凭据类型、赋值路径与用途；源码复核只输出位置、类型和脱敏证据。 | 公钥、公开标识符、环境变量名称、占位符和明确的测试假值不算已确认泄漏。疑似凭据也不能通过远程认证来验证。 |
| 测试代码覆盖率 | 运行项目已有的 coverage 入口，检查其包含 / 排除配置，读取行、分支、函数覆盖与关键错误路径。存在基线时用相同配置比较；变更覆盖需映射到真实变更行。 | 测试通过不等于覆盖充分；有执行覆盖不等于有有效断言。只使用项目或用户规定的阈值；缺报告、缺基线或无法运行时明确未验证，不能编造百分比。 |
| 僵尸文件 | 从应用、测试、构建、脚本、资源和发布入口追踪引用；结合已有未使用文件工具核实整个文件是否不可达。 | 动态路径、文件路由、约定加载、配置引用、资源 URL、生成输入和发布入口会绕开静态 import。单次搜索无命中只算候选。 |
| 僵尸模块 | 检查文件内未使用的模块、函数、类、导出，以及包依赖是否在可执行入口可达的调用图中使用。区分内部冗余与对外发布接口。 | 注册副作用、反射、依赖注入、插件、动态加载和包导出可能没有直接调用；被死文件引用也不证明代码存活。 |
| 僵尸 API | 清点路由、RPC、公开 SDK 接口，核实注册、实现、客户端调用、契约及项目已有使用证据。区分内部不可达接口与仍可被外部调用的接口。 | 仓库内零调用、缺日志或文档缺失不能证明公开 API 无人使用。外部调用证据不足时标待核实；不要自动调用线上接口或建议直接删除。 |

搜索结果用于发现候选；语义、可达性和实际命令结果用于确认。工具配置或命令失败要保留退出码与相关诊断，不得把失败当作“零问题”。日志和报告同样脱敏。

## 3. 执行与等待

小范围直接完成。范围较大且环境支持子 agent 时，可按“分支与错误”“密钥与覆盖率”“僵尸代码与 API”分工；共享同一个范围、基线、排除目录与上述判断边界。

给每个 agent 传递具体检查项、代码路径、工具入口、只读约束，要求返回命令、退出码、发现位置、证据、未验证项。将缺失信息标待核实，避免推测填空。覆盖率等写报告的命令由一个执行者运行，其他 agent 读取结果，避免输出目录冲突。

使用环境真实提供的 agent 等待机制（例如 Codex 的 `collaboration.wait_agent`；其他宿主使用其对应机制）。工具名以当前环境为准，不能把 “Waiting for agent” 状态文字当成可调用工具。等待间隔遵循宿主限制，等待期间可核实已有候选，给用户简短进度。

等待所有已派发检查完成后再汇总；超时、失败或中断按对应检查项标未验证并说明原因。无子 agent 能力时顺序检查，检查标准不变。

## 4. 复核与交付

- 复核所有确认问题：读取准确位置及相关调用链，合并同一根因，给出实际影响和最小修复建议。
- 每项标记为：**通过**（在声明范围内完成且未确认问题）、**发现问题**、**待核实**（存在候选但证据不足）、**未验证**（未执行或执行失败）、**不适用**（说明原因）。同项有多种结果时分别列出，不用一个“通过”掩盖缺口。
- 先列已确认问题，按实际风险排序：`[P1/P2/P3] 文件:行号 — 问题；证据；影响；建议`。紧急且影响已证实的问题可用 P0；候选不冒充确认问题。
- 用检查账本覆盖全部七项，列出状态、命令或搜索依据、退出码和关键结论。命令须包含工作目录及必要参数，供复现；长报告列出文件位置。密钥内容不进入报告或聊天。
- 单独列出待核实候选、执行限制和未验证项。没有确认问题时写“本次范围内未发现已确认问题”，只有全部适用项完成才可称检查完成。

交付以报告为止。用户要求修复时，再按授权范围实施并重跑受影响检查。
